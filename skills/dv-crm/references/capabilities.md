## Role eligibility

All five roles can hold events.read, tasks.read, tasks.write, attention.read; this includes get_whats_new and get_production_schedule. Additional scopes:

| Role | events.status | activity.read | inventory.read | schedule.read | quotes.read | quotes.write | clients.read | equipment.read | equipment.write | labor.finance | schedule.write | events.create | production.write |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| admin | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes |
| manager | Yes | No | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | No | Yes |
| manager_sensitive | Yes | No | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | Yes | No | Yes |
| warehouse_manager | No | No | Yes | Yes | Yes | No | No | Yes | No | No | No | No | No |
| user | No | No | No | No | No | No | No | No | No | No | No | No | No |

Eligibility is not authorization: AI access must be enabled, the connection active, and scope approved. Server discovery and every call enforce the current role/grant. The hub neither enables users nor changes access.

Admin and manager_sensitive create approved tasks and can edit task content. Manager, warehouse_manager and user create pending Open requests. The first four roles can change approved task status; basic users can change only approved tasks directly assigned to them. Pending requests cannot change status before approval. request_task_edit proposes a change to an approved task; the task stays unchanged until an approver accepts it in the CRM (basic users: only tasks they created). review_task_request approves or declines a pending task or edit request, only for roles that can approve tasks (admin, manager_sensitive), and always in two steps (see [safeguards](quotes.md)). No task delete or meeting/invite tools are included. Task updates require the latest updatedAt.

Quote structure is visible to warehouse_manager; money/prices/costs are hidden, and money-containing text can be redacted. Managers and manager_sensitive see quote prices/costs but not profit/margin; admin sees financials: get_quote returns profitAndLoss for admins only, following the quote's saved labor basis (quoted or actual). Basic users have no quote access. Quote writes are inactive drafts only. See [safeguards](quotes.md).

Schedules expose shifts, venue-local times, role assignments and booking status; no crew contact/pay details. list_staffing_gaps shows open, awaiting-reply and declined shifts; find_available_crew returns names only, applying the Scheduler's overlap and approved time off rules. schedule.write (assign_shift, create_shifts, update_shift_times) changes crew and shift times with the CRM's checks; overlaps are refused, on the same event or on another event at a different location; when both shifts are at the same location (such as a shop day shared by two events) assign_shift asks for a confirmation; approved time off needs a confirmation, and invites, WhatsApp requests and calendar events are never sent: send them from the CRM. It needs schedule.read as well. Client tools expose permitted organization/contact/billing details, never quote prices. Real outputs can be sensitive: do not paste them into public issues, examples, or this repository.

equipment.read shows each item's In-House, vendor and unassigned units, shortages and saved logistics, never prices or vendor contacts. A vendor's sectionPresets carry separate pickup and return details for a named group of quote sections (for example one truck); when any exist, answer per preset and name the sections each covers. equipment.write (set_equipment_sources) splits units between In-House, existing vendors and not assigned; the person chooses among unclear vendor names, vendors are never created, and over-allocation needs a confirmation. labor.finance (get_labor_budget, list_labor_budgets) shows labor budget against scheduled cost, including crew pay rates, never contact, tax or payment details.

events.create (create_event, search_venues) is for admins only for now; it also needs events.read, and clients.read helps find the client. create_event needs an existing client (search_clients) and venue (search_venues) and never creates either: if one is missing, stop and ask the person to add it in the CRM. It is always two steps: the first call writes nothing and returns a preview, possible duplicates (same client or venue on the same days) and a confirmationCode; only after the person's explicit yes, call again with the same input, the code and a requestKey. The event starts as Created and is never confirmed; nothing is sent to clients or crew. Bookkeeping receives the CRM's usual new-job alert (tell the person if bookkeepingAlert is failed, partial or uncertain). Day times are local to the venue; search_venues returns id, name, city and state only.

production.write (add_production_rows, update_production_row, remove_production_row) is for admin, manager and manager_sensitive; it also needs events.read, and the Edit permissions picker ticks that See along with it. get_production_schedule is a read under events.read for every role: it returns each day's run-of-show rows (type, time in and out as HH:MM in the venue time zone, location, department, vendor, action, notes, linked shift groups, updatedAt), with no crew names, contact details or money. To change rows, read first and pass the row's updatedAt as expectedUpdatedAt; a stale version is a conflict and nothing is written. add_production_rows adds up to 30 rows to a day (eventDateId or date) all or nothing, with a requestKey (reuse it only to retry). update_production_row changes one row or replaces its linked shift groups. remove_production_row is always two steps: the first call deletes nothing and returns a preview and a confirmationCode; only after the person's explicit yes, call again with the same rowId, expectedUpdatedAt and the code (ten minutes). A removed row cannot be restored with the AI tools. A time that causes an equipment conflict is refused and nothing is written. Nothing is sent to crew; when invitesOutOfDate is true, a calendar invite already sent is out of date and must be resent from the CRM.

Quote add-ons choose exactly one of six Event P&L groups: Labor, Equipment rental & subs, Trucking, Food, Travel & lodging or Misc. Existing add-ons keep their old type until a group is chosen with update_quote_line addonType. A Labor add-on replaces calculated labor in totals and P&L, so confirm with the person before adding one. When a quote ignores rental cost, its cost excludes both rental and custom lines; add-ons and effective labor still count.

Equipment reservation windows are saved per item, falling back to the event's equipment dates. They may have HH:MM times and a time zone: ranges are [start, end), so a 14:00 end and a 14:00 start do not clash. Missing times mean whole days (last day inclusive). Partial windows hold fewer units for part of the dates; returned partials match stock counting, clipped to the item window and capped at the In-House units held. get_event_equipment shows times, zone and partials; get_inventory_availability shows times on holds and counts a same-day flip once. Timed counting applies to shortage/conflict checks in set_equipment_sources, add_quote_lines, add_production_rows and update_production_row; equipment shortages and source/quote-add/quote-update warnings also count other reservations during partial windows. Edit dates, times and partial windows only in the CRM, not through AI tools. A saved equipment plan holds no stock: resolve shortages before reserving.

get_event_equipment pages by whole item. When nextCursor is set, call again with it and the same filters until nextCursor is null before concluding anything about conflicts, shortages or a whole quote. sections matches case-insensitive exact section names (unknown names appear in unmatchedSections); itemIds filters items. Conclusions from filtered reads cover only those items/sections; read without filters for a whole quote. itemsOnly skips summary and logistics; otherwise they appear only on the first page. Use itemsTotal and itemsReturned to describe coverage. A cursor is refused if the event, quote, filters or quote items changed: start over without a cursor. Each item's reservationDates includes timeZoneVenue {id,name} and reservedLines, the CRM's “N units only from / until” sentences: use these when present; when null for older windows, describe the partials. If partials are cut at 20, partialsTotal gives the total; disclose the omitted partials rather than presenting the sample as complete.

Shift groups (create_shift_groups, update_shift_group, delete_shift_group; schedule.write, which also needs schedule.read; admin, manager and manager_sensitive) are the named blocks of hours for one department in the Shifts panel of Schedule Management, with role slots. They are not Production Schedule rows (the run of show). get_event_schedule shows each group with its updatedAt. create_shift_groups adds 1 to 20 groups to event days (eventDateId or date) all or nothing, each with optional open role slots (roleId from list_labor_roles and a count; at most 100 slots per call), HH:MM times in the day's venue time zone (an end at or before the start runs past midnight) and a requestKey (reuse it only to retry; a reused key with different groups is refused). update_shift_group changes one group's name, department, location or hours: pass its updatedAt as expectedUpdatedAt; slots without their own times follow the new hours and slots with their own times keep them (the answer lists both); a change that would overlap an assigned crew member's other booking is refused. delete_shift_group is always two steps: the first call deletes nothing and returns a preview and a confirmationCode; only after the person's explicit yes, call again with the same shiftGroupId, expectedUpdatedAt and the code (ten minutes). A group with any assigned crew or labor company cannot be deleted; a deleted group cannot be restored with the AI tools. Nothing is sent; when invitesOutOfDate is true, a calendar invite already sent is out of date and must be resent from the CRM. add_production_rows now refuses a reused requestKey that carries only part of the earlier rows.

## Write limits per hour
Tasks, approvals and event status: 30 per connection, 60 per person. Shift and shift group changes, production schedule changes, quote building and equipment sources: 60 per connection, 120 per person. Previews that change nothing do not count as writes. Event creation: one event per person per hour; previews and refused attempts do not count.

Activity dates use New York (up to seven days); inventory ranges support up to ten IDs/31 days. Paginated lists and Needs Attention counts may exceed displayed samples. Shift hours must be valid before staffing: invalid windows are refused, and find_available_crew reports crew blocked by an invalid assigned window. Labor budget and quote actual labor use paid hours (minimum call, shifts up to 1 hour apart joined, overtime, double time and flat day rates), so cost is not always hours times rate. Needs Attention card transaction counts follow each card's start date and include charges the bank feed mislabels as a card payment but skip duplicate charges from an old standalone card whose charges now show on its parent card, and Old Westbury requests dismissed by an administrator no longer count as pending attention. A task request or task edit request also notifies reviewers in the Team app.

Reads can record logs and reconcile statuses internally; inventory reads do not reserve stock.
